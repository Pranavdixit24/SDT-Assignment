# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72–74) | Returns static `{"status": "ok"}` without verifying MongoDB connectivity. Fails readiness probe requirement. | Stop MongoDB service; calling `GET /health` still returns 200 OK instead of 503 Service Unavailable. | Added `client.admin.command('ping')` inside a try-except block; returns 200 on success, raises `HTTPException(503)` if MongoDB ping fails. |
| 2 | `list_employees` (line 93) | Off-by-one pagination error: `skip = page * page_size`. On `page=1`, skips items 0–19. | Query `GET /employees?page=1&page_size=20`. The first 20 employees are skipped and never returned. | Changed skip calculation to `skip = (page - 1) * page_size`. Added validation for `page >= 1` and `1 <= page_size <= 100`. |
| 3 | `list_employees` (line 94) | Total count ignores filter: `total = db.employees.count_documents({})` counts the entire collection. | Create 10 employees across 2 departments; query `GET /employees?department=Engineering`. `total` returns 10 instead of 5. | Changed to `total = db.employees.count_documents(q)` so total always reflects applied filters (Rule R10). |
| 4 | `list_employees` (line 95) | Missing sorting requirement: contract specifies results must be sorted by `emp_code` ascending. | Query `GET /employees`. Order is arbitrary/insertion order from MongoDB rather than sorted by `emp_code`. | Added `.sort("emp_code", 1)` to the MongoDB query cursor. |
| 5 | `create_employee` (lines 78–85) | Race condition and missing database unique constraint: uses check-then-insert (`find_one` then `insert_one`). | Send two simultaneous `POST /employees` with the same `emp_code`. Both can succeed without a unique index. | Created a unique index on `emp_code` at app startup, and wrapped insertion in try-except catching `pymongo.errors.DuplicateKeyError` to return 409 Conflict. |
| 6 | `create_employee` / `EmployeeIn` (lines 53–61, 82) | Missing schema validations and instant format: `shift_start == shift_end` allowed, `emp_code` regex unenforced, `created_at` stored as naive local datetime and not returned as epoch ms. | Post employee with `shift_start="09:00"` and `shift_end="09:00"`; passes validation. `created_at` returned as ISO string rather than epoch ms. | Added Pydantic field validators (`pattern` for `emp_code`, `shift_start != shift_end`), stored `created_at` as UTC BSON datetime, and converted to integer epoch ms on output. |
| 7 | `compute_late_minutes` (lines 33–37) | Incorrect late calculation & grace period condition: calculates integer minutes first, then checks `minutes > 10`. | Shift start 09:30, punch-in 09:40:01 (601 seconds late). `int(601/60)` is 10; `10 > 10` is False, returning 0 late minutes instead of 10 (violates Rule R2). | Checked strict grace period on total seconds (`(punch_in - start).total_seconds() > 600`), then computed `int(total_seconds // 60)` from `shift_start`. Handled IST timezone and overnight shift start times. |
| 8 | `compute_work_hours` (lines 40–41) | Python's built-in `round()` uses round-half-to-even (banker's rounding) rather than decimal half-up required by Rules R4 and R8. | Work duration of 2.625 hours gives `round(2.625, 2) == 2.62` instead of `2.63`. | Replaced with `decimal.Decimal` arithmetic using `ROUND_HALF_UP` to round strictly half-up to 2 decimal places. Also truncated input instants to whole seconds first (Rule R1). |
| 9 | `compute_overtime` (lines 44–47) | Missing 30-minute threshold check and broken overnight shift calculation: returns overtime under 30 mins, and computes wrong end datetime across midnight. | Punch-out 15 minutes after shift end returns 15 (should be 0 under Rule R3). Overnight shift (22:00–06:00) sets end on previous day, giving 16+ hours overtime. | Added check that overtime must be `>= 30` minutes, otherwise returns 0; properly calculated `shift_end` on the following calendar day for overnight shifts (`shift_end <= shift_start`). |
| 10 | `punch_in` (lines 101, 113) | Unhandled `None` when employee is not found causes `TypeError` resulting in a 500 error instead of 404. | `POST /attendance/punch-in` with non-existent `emp_code="EMP9999"`. Returns 500 Internal Server Error because `emp["shift_start"]` fails. | Added explicit check: if `emp is None`, raise `HTTPException(404, "Employee not found")`. |
| 11 | `punch_in` (lines 104–118) | Race condition on attendance punch-in: check-then-insert allows duplicate attendance records for the same employee and date under concurrency. | Send two simultaneous punch-in requests for the same employee and date. Both can pass `find_one` and create duplicate records. | Created a compound unique index on `(emp_code, date)` at startup, and caught `DuplicateKeyError` to return 409 Conflict. |
| 12 | `punch_in` (lines 102–103) | Improper date calculation and timezone handling: naive `datetime.fromtimestamp` ignores IST calendar date and overnight shift rule R1. | Punch-in at 00:30 IST for an overnight shift (22:00–06:00). Sets `date` to current day instead of the previous day when the shift started. | Converted timestamps to IST (UTC+05:30); for overnight shifts (`shift_end <= shift_start`), if punch-in IST time `< shift_end`, assigned `date` to previous calendar day. |
| 13 | `punch_in` & `list_attendance` (lines 119, 149) | Pollution of API response with internal MongoDB `_id` renamed to `id`. Contract states attendance records have no ID. | Calling `/attendance/punch-in` or `/attendance` returns JSON objects containing `"id": "6688..."`. | Removed `"id"` field from response dictionaries; attendance records are identified purely by `(emp_code, date)`. |
| 14 | `list_attendance` (lines 144–147) | Full collection memory loading and Python in-memory sorting: scales horribly, crashes on 100k documents. | Querying `/attendance` with 100,000 records in MongoDB exhausts server memory and causes timeouts. | Replaced with database-level execution: `db.attendance_logs.find(q).sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` backed by compound indexes. |
| 15 | `list_attendance` (lines 137–141) | Missing date range validation: `date_from > date_to` is not validated and returns empty list instead of 422. | `GET /attendance?date_from=2026-07-10&date_to=2026-07-01`. Returns 200 with empty list instead of required 422 Unprocessable Entity. | Added explicit validation: if `date_from and date_to and date_from > date_to`, raise `HTTPException(422, "date_from must be <= date_to")`. |
| 16 | Startup indexes (global) | No indexes created on startup: database defaults only have `_id` index. | Running explain on `/attendance` or `/employees` results in `COLLSCAN` (full collection scans) on 100k records. | Implemented FastAPI lifespan startup handler to create indexes idempotently on `employees` and `attendance_logs`. |

## Items examined and decided NOT to be defects
1. **`load_dotenv()` with environment fallback**: `os.getenv("MONGO_URI", ...)` correctly reads environment variables with `.env` as fallback, satisfying the rule that real environment variables injected by the grader take precedence.
2. **Shift default times (`09:30` and `18:30`)**: These default values match the defaults defined in the OpenAPI schema.
3. **Pydantic for request/response serialization**: Using Pydantic models for structured validation conforms with FastAPI best practices and OpenAPI schema generation.
